# NavSafe dev — Kubernetes job manifests

Every GPU stage for the three pilot seeds, one manifest per (seed, stage).
Generated by `nexussim/navsafe/world/k8s_jobs.py`; **regenerate rather than
hand-edit**, so a manifest can never drift from the code that produced it:

```bash
python3 nexussim/navsafe/world/k8s_jobs.py \
  --seed /avl-west/navsafe_dev/seeds/<SEED> --stage <aux|train|export|eval> \
  [--regime log_replay|idm] --out <path>
```

## Stages

| dir | image | what it does | cost |
|---|---|---|---|
| `aux/` | `nre-tools-ga` | `ncore-aux-data`: ego masks + semantic seg | ~30 min, 1 GPU |
| `train/` | `nre-ga` | `car2sim_6cam_static`, 160k iters, 5M gaussians | **~5h45m**, 1 GPU |
| `export/` | `nre-ga` | usdz (+ plys, world-frame tracks) | ~2 min, 1 GPU |
| `eval/` | `nre-ga` | serve-grpc **+** closed-loop rollout, same GPU | ~19 min, 1 GPU |
| `serve/` | `nre-ga` | standalone renderer Deployment + Service | interactive use only |

`eval/` has one manifest per interaction regime (`-log_replay`, `-idm`), because
the same seed is scored under each and they must not collide on a job name.
Note the file name keeps the underscore while the job name inside uses a hyphen:
k8s object names are RFC 1123 subdomains and cannot contain `_`.

## Not here: ncore and arrow

The two CPU stages have no manifest. They need py123d + nuplan-devkit, which
live in the work pod, and they use no GPU:

```bash
python3 nexussim/navsafe/world/run_ncore.py --seed /avl-west/navsafe_dev/seeds/<SEED>
python3 nexussim/navsafe/world/run_arrow.py --seed /avl-west/navsafe_dev/seeds/<SEED>
```

Both stage the log db to **container-local disk** first. The nuPlan devkit ORM
issues ~17 M page reads against a single 55 MB db; on CephFS that is tens of GB
of network round-trips and the process sits in D-state for half an hour.

## Order, and what each stage waits for

```
run_ncore.py ─┐
              ├─> aux/ ─> train/ ─> export/ ─> eval/
run_arrow.py ─┘
```

`runner/pipeline.py` submits these in order, judging each stage by **its output
on disk**, not by job history — so an interrupted run resumes by re-invoking the
same command, and a job that succeeded but wrote nothing is correctly treated as
incomplete.

Two completion checks are deliberately narrower than they look:

* **ncore** is judged by `nurec_origin_offset.json`, not the manifest. A store
  built without `NCORE_REREF_FRAME0` is silently jittery (float32 holding
  absolute UTM has a ~0.5 m ULP), and the mistake only surfaces after a 5-hour
  training run.
* **aux** requires all five outputs, not a glob. `ncore-aux-data` writes its
  shards progressively, and training that starts on a half-written shard dies
  with `IndexedTarStore: invalid index header`.

## Running one by hand

```bash
kubectl apply -f train/5166e079c1185f4c.yaml
kubectl logs -n cogrob -l k8s-app=navsafe-dev-train-5166e079c1185f4c -f
```

Every stage is idempotent — it short-circuits when its output already exists —
so re-applying after a pre-emption is safe.
